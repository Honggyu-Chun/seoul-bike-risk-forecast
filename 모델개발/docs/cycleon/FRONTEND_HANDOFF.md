# 프론트엔드 인수 명세

> Draft v0.1 · 위치·예정 정각·위험·거리 비교 화면의 개발 기준이다. 최종 UI 디자인을 지정하지 않는다.

## 1. 권장 사용자 흐름

1. 사용자 위치를 입력하고 팀 백엔드의 상태·대여소 목록을 가져온다.
2. AI status.supported_targets의 지원 목표 **정각** 3개를 KST로 표시한다.
3. 지도 범위/선택 대여소 ID와 해당 horizon으로 예측을 요청한다.
4. 최신 수량, 목표 정각, 0대 위험 확률, 이용 가능 여부를 각각 표시한다.
5. 위치·같은 horizon·사용자가 정한 반경으로 추천을 요청한다.
6. 추천·대안 또는 보류 안내를 표시한다. 빈 응답이면 자동으로 반경을 확대하지 않는다.

14:40 KST에서 “1시간 뒤”만 쓰면 15:40으로 오해할 수 있다. “15:00 이용 / 14:00 기준 예측”처럼 실제 시각을 표시한다. 15시로 넘어가면 status를 다시 조회해 선택한 horizon과 target_at의 대응을 갱신한다. 지난 요청이 늦게 도착하면 최신 선택 화면을 덮지 않도록 요청 순서를 관리한다.

## 2. 표시할 데이터

| 화면 값 | 출처·표시 규칙 |
| --- | --- |
| 대여소 이름/위치 | 팀 백엔드 대여소 목록. predictions에는 이름·좌표가 없음 |
| 현재 확인 수량 | latest_inventory. null이면 “자료 없음”, 0이면 실제 “0대” |
| 수량 갱신 시각/나이 | latest_inventory_received_at / age_seconds |
| 이용 목표 시각 | target_at을 KST로 변환 |
| 0대 위험 | risk_probability×100, null이면 확률 미표시 |
| 위험 판정 | is_risk. 모델이 보정한 임계값 판정이며 클라이언트 0.5 고정 금지 |
| 모델·입력 경로 | 진단 영역의 model_id/input_group. 일반 사용자 화면의 필수 노출 아님 |
| 거리 | 추천의 distance_m. 직선거리임을 표시하고 도보 시간으로 부르지 않음 |
| 추천 | recommended 1곳과 alternatives 최대 2곳 |

`risk_probability`는 정확한 미래 자전거 수량도 대여 성공 확률도 아니다. `score`는 거리 가중치가 포함된 내부 정렬 점수이므로 위험 퍼센트처럼 표시하지 않는다. 기본 모델/개발 수치를 운영 성능이나 실제 이동시간 절감으로 제시하지 않는다.

## 3. 화면 상태 매핑

| 응답 | 화면 처리 예시 |
| --- | --- |
| status ready + 유효 확률 | 목표 정각의 부족 위험과 최신 수량 표시 |
| 일부 items만 null | 해당 대여소에만 “예측 준비 중/예측 불가” 표시 |
| is_risk=false | 모델 임계값 아래. 자전거 보장 또는 “안전 확정”으로 표시하지 않음 |
| latest_inventory=0 | 현재 0대 표시. 미래 예측 값은 별도 표시 가능 |
| age_seconds≥300 또는 null/음수 | 최신성 경고. 현재 추천의 신선도 기준 미충족 |
| base_not_precomputed | “기준 시각 예측 갱신 중”. 제한된 재조회 |
| recommendation_policy_not_selected | “추천 기능 준비 중”. 대여소 비교 UI는 계속 사용 |
| no_station_within_radius | “선택 반경에 대여소가 없습니다”. 사용자가 반경 조정 |
| no_fresh_positive_eligible_prediction | “현재 추천 가능한 대여소가 없습니다” |
| status not_ready | 준비 중 상태. 항목별 null 사유 유지 |
| 401 | 사용자 로그아웃으로 단정하지 말고 중계 서버 설정 문제로 처리 |
| 422 | 선택값·요청 형식 수정 |
| 연결 실패/timeout/500 | “잠시 조회할 수 없습니다”, 재시도 제공 |
| 알 수 없는 reason | 일반 예측/추천 불가 처리. UI가 깨지지 않게 함 |

확률이 0일 때도 `if (!p)`로 누락 처리하지 않는다. `p === null`로 확인한다. 추천 보류 필드는 `abstained`이며 `abstain`이 아니다.

## 4. 인증과 호출 경계

브라우저 → **팀 애플리케이션 백엔드** → AI 서비스 순서다. 프론트에는 CYCLEON_SERVICE_TOKEN이나 공공 API 키가 없어야 한다. 현재 AI에는 브라우저 직접 접속을 위한 CORS 설정이 없다. `/internal/ai-data/v1/*`도 공개 프론트용 API가 아니다.

앱 백엔드의 공개 경로는 아직 이 AI 계약에서 정하지 않았다. 프론트와 백엔드가 합의한 경로로 호출하되 body와 응답은 [AI 레퍼런스](API_REFERENCE.md)를 보존한다. 앱 자체 대여소 목록·인증·사용자 위치 처리 등은 서비스 팀의 구현 범위다.

## 5. 지금 개발하는 방법

[빠른 시작](QUICKSTART.md)의 로컬 AI 모의 서버를 사용한다. 기본형은 추천 정책 미선정, `recommendation-demo`는 합성 추천 성공, `not-ready`는 확률 미준비다. 모델 파일 없이 이 세 시나리오를 개발할 수 있다. `model_stage=mock_no_model_no_live_data`와 고정 시각을 개발 화면/테스트에서 확인한다.

전체 응답은 [합성 JSON](mock_examples.json)에 있고 Postman collection은 기본 모의 주소를 사용한다. 앱 백엔드가 준비되기 전에는 같은 JSON fixture를 프론트 테스트에서 읽어도 된다. 합성 recommendation-demo 결과는 실모델의 추천이 가능하다는 증거로 쓰지 않는다.
