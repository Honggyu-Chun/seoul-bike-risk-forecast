# GFS 이전 예보의 실시간 입력 적격성

검토일은 2026-10-20로 한다. 결론은 **현재 수신 경로가 확인된 조건부 추가 모델 실험에는 사용할 수 있으나, 2025년 당시 실시간 성능이 검증된 입력으로 확정하지 않는다**로 정리한다. 이 단계에서 모델을 학습하지 않고 대용량 자료를 추가 수집하지 않는다. KOPIS에 요청하지 않는다.

## 현재 메타데이터의 실제 확인

[공식 갱신 문서](https://open-meteo.com/en/docs/model-updates)는 초기화·변환 완료·API 제공 시각을 구분한다. 문서의 동적 표 주소를 추정하지 않고 공식 `open-meteo/open-meteo-website` 저장소의 `src/routes/en/docs/model-updates/+page.svelte`에서 확인한다. 소스 51~67행의 주소 생성과 366~377행의 GFS 0.11° 항목을 대조해 아래 주소를 확인한다. 소스 트리 식별자와 원문을 이 폴더에 보관한다.

`https://api.open-meteo.com/data/ncep_gfs013/static/meta.json`

이 주소를 **한 번** 조회하고 HTTP 200의 608바이트 JSON을 저장한다. 원문은 `gfs013_metadata_current_20261020.json`, 출처·수신 시각·SHA-256·계산 근거는 `gfs013_metadata_audit.json`에서 확인한다.

| 항목 | UTC | 서울 시간 |
| --- | --- | --- |
| 현재 마지막 실행 초기화 | 2026-10-20 00:00:00 | 2026-10-20 09:00:00 |
| 다운로드·변환 완료 | 2026-10-20 05:23:31 | 2026-10-20 14:23:31 |
| 실제 API 제공 시각 | 2026-10-20 05:44:23 | 2026-10-20 14:44:23 |
| 이번 응답 수신 | 2026-10-20 08:48:09.370407 | 2026-10-20 17:48:09.370407 |

초기화부터 API 제공까지 5시간 44분 23초, 약 5.7397시간으로 계산한다. 갱신 주기는 21,600초(6시간), 시간 해상도는 3,600초(1시간)로 확인한다. 변환 완료 시각을 공개 시각으로 대체하지 않는다. 공식 문서가 안내하는 서버 간 전파 여유 10분을 별도 고려한다. 이 한 번의 응답으로 장애·지연의 최대값을 보장하지 않는다.

## 저장한 2025년 자료의 선행시간을 해석하는 방법

[Previous Runs 공식 설명](https://open-meteo.com/en/docs/previous-runs-api)은 `_previous_day1`을 유효 시각보다 24시간 앞선 예보 오프셋으로 정의하고, 개별 실행 초기화가 필요한 경우 Single Runs를 사용하도록 안내한다. 저장한 요청은 `models=gfs_global`을 명시하며 기온·강수·습도·풍속·운량의 day1 계열만 사용한다. 과거 관측이나 사후 재분석으로 이 열을 대체하지 않는다.

추가로 공식 API 저장소의 현재 구현을 검토한다. `OmFileSplitter.swift` 363~365행은 day1 저장 시 처음 24시간에 해당하는 단계를 건너뛰고, 441~450행은 허용된 이후 구간의 값으로 기존 파일을 갱신하는 구조를 보인다. `GfsDomain.swift` 108~124행은 6시간 갱신과 1시간 격자를 나타낸다. 따라서 **24시간 오프셋을 각 행이 정확히 같은 24시간 선행의 단일 실행에서 나왔다는 증거로 바꾸지 않는다**. 현재 저장 구조를 근거로 최소 선행시간을 고려할 수 있으나, 현재 코드를 2025년 모든 생성·재처리의 증명으로 소급하지 않는다.

기존 수집 manifest의 `fixed_lead_hours=24`는 서비스의 명목 day1 오프셋으로 해석한다. 개별 행의 실행 ID·초기화 시각·당시 제공 시각이 실제 JSON에 들어 있는 것은 아니다. 이러한 필드가 없다는 사실을 보존하고, `valid_time-24h`로 가상의 `issued_at`이나 `received_at`을 만들지 않는다.

## t+1 예측에 적용할 여유와 남은 불확실성

유효 시각 V가 자전거 예측의 t+1시간이고 예보 실행이 V보다 최소 24시간 앞선다는 조건을 두면, 실행 초기화와 입력 t 사이에 최소 23시간의 간격이 생긴다. 현재 관측한 5.7397시간 지연과 10분 전파 여유를 차감하면 약 **17.09시간의 명목 여유**가 남는다고 계산한다. 이는 조건을 둔 산술이며 2025년의 실제 모든 공개 시각을 측정한 결과가 아니다.

현재 경로에 대해서는 이미 저장한 `gfs_day1_live_20261020_audit.json`을 함께 확인한다. 서울 시간 16:00:08에 18:00 유효 예보를 받은 기록이 있으므로, 미래 목표 시각 이전에 day1 계열 예보를 받는 현재 경로 자체는 실제로 확인한다. 그러나 이번 메타데이터는 현재 최신 GFS 실행의 상태이며, 별도 호스트의 previous-runs 응답에 들어 있는 모든 값과 실행 ID가 일치함을 보장하지 않는다. 두 기록의 조회 시각도 서로 다르므로 원자적인 동일 실행 검증처럼 결합하지 않는다.

2025년 JSON에는 행별 초기화·공개·수신 시각과 당시 수정 이력이 없다. 서비스 장애 후 나중에 복구·재구성된 값이 있었는지도 확인하지 않는다. 현재 6시간 주기가 모든 실행이 제때 공개됐다는 증거는 아니다. [Single Runs 공식 설명](https://open-meteo.com/en/docs/single-runs-api)은 일반 모델의 실행별 보존을 2026-04-02부터 안내하므로 GFS의 2025년 이력을 해당 API로 전부 복원했다고 주장하지 않는다.

## 적용 결정과 비교 방법

| 목적 | 판단 | 반드시 붙일 조건 |
| --- | --- | --- |
| 현재 API에서 t 이전에 받은 미래 예보 사용 | 경로 확인으로 판단한다. | 원문과 실제 `received_at`을 저장하고 목표 유효 시각을 정확히 연결한다. 응답 실패·미수신 값은 결측으로 둔다. |
| 2025년 저장 day1 자료의 추가 특징 비교 | 조건부 연구 실험의 후보로 채택할 수 있다고 판단한다. | `forecast_offset_archive_conditional`, `historical_reception_verified=False`, `per_row_run_publication_verified=False`를 기록한다. 동일 모델·동일 기간에서 예보 추가 효과만 비교한다. |
| 과거 당시 실시간 모델 성능을 검증했다는 주장 | 증거가 부족해 채택하지 않는다. | 현재 조회 성공과 명목 여유만으로 당시 공개본 일치를 인증하지 않는다. |
| 실제 운영 모델의 최종 채택 | 성능과 수신 검증 뒤에 판단한다. | 실제 받은 스냅샷을 축적해 실행 교체·지연·누락과 예측 성능을 함께 확인한다. |

대안으로 day2 같은 더 오래된 오프셋을 쓰면 명목 여유는 커지지만 당시 수신·수정 이력 미확인을 해결하는 것은 아니며 예보 정보가 더 오래된다는 비용을 가진다. 현재 관측 날씨의 사후 확정값을 사용하는 대안은 미래 날씨 입력의 제공 가능성 문제를 해결하지 못한다. 개별 실행과 제공 시각을 함께 보존한 자료를 확보하는 방법이 가장 직접적인 검증으로 남는다.

새 키나 유료 API 결제는 현재 소량 메타데이터 확인과 조건부 비교에 필요하지 않다. 2025년의 행별 제공 이력을 엄격하게 요구한다면 제공기관이 보유한 원 실행·배포 기록 또는 당시 직접 보존한 스냅샷이 필요하다. 이 자료는 현재 보유하지 않으며 사용자 대신 외부 문의를 보내지 않는다. 유료 가입이 과거 제공 기록까지 자동 보장한다고 가정하지 않는다.

## 보존 기록

처음 전원 대비에 만든 `보존검수.json`은 당시 상태의 기록으로 유지하고, 동일 바이트를 `최초보존검수_20261020T070339Z.json`에도 보존한다. 그 뒤 문서와 코드가 변경됐으므로 최초 해시와 현재 파일이 일부 다를 수 있음을 명시한다. 최신 자료·문서·참조 소스·운영 입력 코드의 해시는 `보존검수_최신_20261020.json`에 별도로 저장한다. 최신 파일은 최초 시점의 테스트와 현재 메타데이터 검증 범위를 구분해 기록한다.
