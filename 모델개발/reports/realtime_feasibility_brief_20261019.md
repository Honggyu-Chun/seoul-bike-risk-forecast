# 실시간 입력을 이용한 따릉이 예측 가능성

확인일: 2026-10-19, 한국시간 기준.

## 결론

**현재 수량을 실제로 받아오는 공식 경로가 동작한다.** 공개 샘플을 두 번 호출해 정상 응답과 수량 변화까지 확인했다. 따라서 실시간 입력을 수집해 예측에 넣는 구조는 추진할 수 있다. 다만 발급키를 이용한 서울 전체 조회·주기 저장·5~10분 뒤 모델 정확도는 아직 검증하지 않았다.

## 직접 확인한 내용

- [서울시 공식 실시간 대여정보](https://data.seoul.go.kr/dataList/OA-15493/A/1/datasetView.do): 현재 대여가능 수량·위치 제공, 실시간 갱신 안내, 1회 최대 1,000행 안내 확인.
- 공개 샘플 `http://openapi.seoul.go.kr:8088/sample/json/bikeList/1/5/`에서 HTTP 200, `INFO-000`, 대여소 5행을 두 차례 실제 수신했다. 요청 서비스명은 `bikeList`, 응답의 최상위 자료 이름은 `rentBikeStatus`였다.
- 21:26경 첫 조회에서 102번 망원역 1번출구 앞 수량은 29대, 21:28경 재조회에서는 30대였다. 나머지 4행은 두 응답에서 동일했다. 이는 두 조회에서 값이 실제로 변했다는 근거이며, 정확한 원천 관측 시각이나 항상 일정한 갱신 주기를 보장하는 근거는 아니다.
- 수량은 `parkingBikeTotCnt`, 위치는 `stationLatitude`·`stationLongitude`, API ID는 `stationId`로 확인했다. `rackTotCnt`는 거치대 수로, 현재 자전거 수 대신 사용하지 않는다.
- API ID는 `ST-4`처럼 과거 파일의 숫자 번호와 형식이 달랐다. 샘플 5행은 대여소 이름 앞 숫자로 과거 위치 번호와 연결됨을 확인했다. 서울 전체 ID 대응은 별도 검증이 필요하다.
- 응답에 대여소별 원천 관측 시각은 없었다. 우리 요청·수신 시각을 저장하고 원천 갱신 지연은 반복 관찰·제공기관 확인으로 검증해야 한다.

## 사용 조건과 다음 단계

1. [공식 이용 안내](https://data.seoul.go.kr/together/guide/useGuide.do)에 따라 일반 인증키를 발급받아 서버 환경변수로 설정한다. 샘플키는 5행 제한이며 전체 수집용으로 쓰지 않는다.
2. 발급키로 실제 대여소 수·페이지 분할·호출 제한을 확인한다. 샘플 응답의 `list_total_count=5`를 서울 전체 개수로 해석하지 않는다.
3. 대여소 ID 대응과 수량 의미·갱신 지연을 점검하고, 허용 범위에서 1~5분 간격 등의 주기 수집을 설계한다. 사용자 접속 때마다 원천 API를 호출하기보다 서버에서 수집·저장한 자료를 제공한다.
4. 같은 간격으로 모은 기록에서 5분 뒤·10분 뒤의 0대 여부를 각각 정답으로 만들고, 같은 조건의 현재 상태 유지·자기 정보 AI·주변 정보 AI를 비교한다.
5. 과거 1시간 파일은 1시간 모델의 출발점이며, 짧은 간격 모델의 성능을 대신 증명하지 않는다. 기존 1시간 모델에 실시간 입력만 넣었다고 10분 모델이 되는 것은 아니다.

호출량 예: 서울 전체가 N개이고 1회 1,000행까지라면, 전체 한 번 조회에 필요한 호출은 `ceil(N/1000)`회다. N=3,000을 **가정**하면 5분 간격 수집은 하루 864회, 1분 간격은 4,320회다. 현재 서울 대여소 수를 실제로 확인한 수치가 아니며 실제 키의 허용량과 대조해야 한다. 일반 가이드의 하루 1,000건 안내는 실시간 지하철 API에 대한 문구이므로 따릉이 일일 제한이라고 옮겨 적지 않았다.
